# Журнал проекта

## Возможности

В параметрах проекта администратору доступна кнопка «Журнал». Участник без
административной роли не получает журнал ни в UI, ни через API.

Фиксируются создание проекта, название и описание, аватар, архивирование и
восстановление, приглашение и повторная отправка, принятие и удаление приглашения,
добавление и удаление участника, изменение роли, категории, создание и удаление
шаблона задачи. Записи содержат время, автора, объект изменения и прежнее/новое
значение, где это применимо. Журнал доставки SMTP и история самих задач остаются
отдельными механизмами.

Журнал появляется с момента установки обновления. Старые события не
восстанавливаются и не выдумываются. Сохраняются последние 2000 событий проекта;
текстовые значения ограничены первыми 500 символами. Это ограниченный
операционный журнал, не бессрочное архивное хранилище. Удаление проекта удаляет
его журнал. Клиентский API не позволяет редактировать или удалять отдельные
записи. Токены, содержимое писем и ключи хранения в журнал не включаются.

## API и согласованность

- `GET /api/projects/:projectId/activity?page=1&limit=20`: только администратор;
  ответ `items, total, page, limit, capacity`, максимум 100 записей за страницу.
- `PATCH /api/projects/:projectId/members/:userId`, тело `{ "role": "admin" }`
  либо `member`: изменение роли администратором. Последнего администратора
  понизить нельзя.

Изменение проекта и его журнал сохраняются одним MongoDB-документом.
Оптимистическая проверка версии защищает от перезаписи параллельного изменения.
Конфликт возвращает HTTP 409: обновите данные и повторите действие.

Добавление участника, членство в организации и запись намерения отправить письмо
сохраняются общей транзакцией. SMTP отправляет существующий worker после commit,
а не внутри транзакции. Подтверждение email также атомарно сохраняет пользователя,
принятые приглашения, назначение задач и уведомления. Сбой не расходует ссылку.
При входе подтверждённого обычного пользователя сервис повторно проверяет
действующие ожидающие приглашения. Ошибка восстановления не блокирует вход и
повторяется при следующей авторизации. Просроченные приглашения не принимаются.

## Требования к выпуску

Нужен MongoDB replica set или sharded cluster с транзакциями. MongoDB Atlas
поддерживает этот режим; одиночный standalone mongod не подходит. Не отключайте
транзакции при ошибке подключения: это нарушит согласованность прав и данных.

Обновите backend и frontend. Существующие проекты не требуют миграции или
пересоздания. Проверьте после выпуска журнал одного тестового проекта и
приглашение собственного тестового пользователя. Реальную доставку письма
проверяйте отдельно: принятие SMTP-сервером не гарантирует попадание во входящие.

## Тесты

Из папки backend:

```sh
npm test
# Укажите адрес отдельного тестового replica set, не рабочую базу:
TEST_MONGODB_URI='mongodb://127.0.0.1:27017/test?replicaSet=rs0' npm run test:integration
```

Интеграционные тесты создают уникальные тестовые базы и удаляют их после проверки.
Они не читают backend/.env. Без TEST_MONGODB_URI проверки с базой пропускаются.
Новые suites: project-activity.test.js, project-activity.integration.test.js,
auth-invitations.integration.test.js. Проверяются права, типизированные ссылки
на пользователей, откат членства при конфликте, одноразовое подтверждение,
восстановление приглашений и отсутствие дубликатов.
