## Восстановление доступа, безопасность и отчёты (пункты 2–5)

### Восстановление пароля

На странице входа появилась ссылка «Забыли пароль?». Ссылка из письма действует 30 минут, используется один раз; повторный запрос не чаще раза в минуту. Для отсутствующего, заблокированного или неподтверждённого аккаунта возвращается тот же нейтральный ответ, но письмо не отправляется. Подтверждение регистрации остаётся отдельным сценарием.

После восстановления или смены пароля отзываются все прежние JWT-сессии, нужно войти повторно. Уже выданные обычным пользователям токены сохраняют совместимость до первой смены пароля. Токены восстановления хешируются; тело письма временно хранится в закрытом outbox/очереди и не возвращается в API пользователя.

API:
- `POST /api/auth/password/forgot`: `{ email }`, ответ 202.
- `POST /api/auth/password/reset`: `{ token, password }`, ответ 200; просроченная или использованная ссылка возвращает 400.
- `PATCH /api/auth/password`: текущий и новый пароль, затем повторный вход.

### Обязательное действие при деплое: суперадминистратор

Автоматическое создание/повышение прав администратора при логине и предустановленные пароли удалены. Старые сессии администратора больше не принимаются. Пароль администратора должен содержать минимум 12 символов, буквы, цифры и специальный символ, максимум 72 байта UTF-8.

1. Убедитесь, что почтовый ящик администратора доступен вам, SMTP работает, `CLIENT_URL=https://taskspot.ru`, а `BACKGROUND_WORKERS_ENABLED=true` хотя бы на одном экземпляре backend. Код приходит именно на email администратора, не на адрес отправителя no-reply.
2. В контейнере backend временно задайте `ADMIN_EMAIL` (существующий адрес администратора), `ADMIN_PASSWORD` (новый уникальный пароль), при создании можно также задать `ADMIN_NAME`. Используйте защищённые переменные или скрытый ввод терминала, не добавляйте пароль в Git, командную историю или `VITE_*`.
3. Из папки backend выполните:

```bash
npm run admin:setup -- --rotate-password
```

Для нового аккаунта: `npm run admin:setup`. Для осознанного назначения существующего обычного пользователя: `npm run admin:setup -- --promote`. Команда не разблокирует аккаунты. Удалите временную `ADMIN_PASSWORD` из окружения после выполнения.

Вход в админку: пароль → шестизначный код из письма. Код действует 10 минут, допускает 5 проверок, повторная отправка через минуту. Сессия администратора действует 30 минут. Во вкладке «Безопасность» можно сменить пароль и завершить сессии. Если почта недоступна, обхода кода нет: восстановите почтовый доступ. Не выполняйте настройку администратора в автоматическом startup/deploy hook.

`POST /api/auth/login` для администратора возвращает `requiresAdminCode` и `challengeId`, но не JWT. Следующий запрос: `POST /api/auth/login/code` с `{ challengeId, code }`.

Ссылки и коды проходят через существующую надёжную очередь. Проверка после деплоя: `npm run smtp:check`, `npm run email:queue`, затем тест на вашем почтовом ящике. Принятие письма SMTP-сервером не гарантирует доставку во входящие. Не выключайте TLS и не обходите подтверждение входа для диагностики. На reverse proxy дополнительно ограничьте частоту auth-запросов: существующий IP limiter приложения хранится в памяти отдельного процесса.

### Отчёты в разделе «Контроль»

Вкладка «Отчёты за период»: от 1 до 92 дней, выбор проекта, группировка по проектам, ответственным, категориям и дням. Созданные и закрытые задачи сравниваются с предыдущим периодом такой же длины. Даты считаются по Москве.

Дата закрытия берётся из последнего события перехода в `closed`, а не `updatedAt`. Старые закрытые задачи без такого события не включаются в показатели закрытий; отсутствующие даты не выдумываются. Нагрузка и просрочки относятся к текущему моменту, архивные проекты не увеличивают текущую нагрузку. В категориях задача может учитываться несколько раз, общий итог остаётся уникальным.

Экспорт: CSV с UTF-8 BOM и разделителем «;», совместимый с Excel. Отдельно выгружается группировка и список задач, созданных или закрытых в выбранный период. Формулы в пользовательских полях экранируются. Нативный XLSX не создаётся.

API: `GET /api/reports/period?from=YYYY-MM-DD&to=YYYY-MM-DD&projectId=...`. Для CSV: `format=csv&group=projects|assignees|categories|daily|tasks`. Права совпадают с видимостью задач: обычный участник не получает чужие скрытые задачи через отчёт или экспорт. Ограничение выгрузки: 20 000 подходящих задач.

### Продуктовая аналитика

Админка → «Развитие продукта»:
- когорта регистраций за выбранный период, подтверждение email, собственный проект, первая созданная задача (в том числе в чужом проекте), просмотр тарифов, оплата;
- пользователи без первой задачи и возвраты в другой день;
- возврат ровно на 7-й календарный день (D7), только для пользователей с полным периодом наблюдения;
- ежедневная активность и сумма подтверждённых оплат за период.

Это независимые показатели, а не обязательная линейная воронка: приглашённый участник может не создавать собственный проект. Достижения когорты показаны на текущий момент. Оплаты считаются по `BillingRequest.payment.status=paid` и `paidAt`, с положительной суммой; ручное бесплатное назначение тарифа не становится выручкой. Возвращённые платежи исключены. Это операционный показатель, не бухгалтерский отчёт.

Новая коллекция `ProductEvent` хранит только ID пользователя, тип события, день и время. Уникальный индекс `user + event + day` защищает от дублей при повторных запросах и нескольких вкладках. Клиент не передаёт произвольный ID пользователя или время; события принимаются только после авторизации обычного пользователя. Нет сбора содержимого задач, паролей, email, IP или записи экрана.

Посещения фиксируются при открытии авторизованной страницы и возвращении на вкладку; системный опрос уведомлений не считается посещением. Истории до внедрения нет: до накопления данных D7 отображается прочерком. Просмотры тарифов и возвраты отмечены «с начала наблюдений». Историческая активация восстанавливается из существующих проектов и задач, поэтому удалённые объекты не учитываются. События пока сохраняются без автоматического удаления; срок хранения и описание аналитики необходимо включить в политику сервиса.

API: `POST /api/analytics/events` (`active_day` или `billing_viewed`); `GET /api/analytics/product?from=...&to=...` только для суперадминистратора. Когорта ограничена 10 000 регистрациями; при превышении сократите период.

### Проверки перед выпуском

```bash
cd backend
npm test
# Для интеграционных проверок задайте TEST_MONGODB_URI отдельного тестового сервера:
node --test test/account-security.integration.test.js

cd ../frontend
npm test
npm run lint
npm run build
```

Интеграционные тесты создают и удаляют собственную уникальную тестовую БД, не используют backend/.env. Без `TEST_MONGODB_URI` пропускаются. Новые проверки: одноразовые ссылки, конкурирующий reset, отзыв JWT, обязательный код администратора, предел попыток, права отчётов, дедупликация событий, CSV, сравнение периодов и D7. Проверка реальной доставки писем и визуальная проверка на production после обновления остаются отдельными приёмочными шагами.
